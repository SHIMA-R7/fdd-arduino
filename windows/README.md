# Windows用フロッピー・ツール

1.44 MB FAT12（3.5インチ2HD）のファイル一覧、取り出し、書き込み、削除、イメージ保存・復元、通常／クイックフォーマットを操作できます。テスト用のFDで書き込みを確認してから使ってください。

## 実行

Python 3（Tkinterを含むWindows版）とpySerialを使います。ATmega328PのFDD基板をUSBシリアルで接続し、GUIで該当するCOMポートを選びます。FTDIのD2XXドライバーが利用できれば低遅延接続を使い、それ以外では通常のCOM接続を使います。

```powershell
py -3 -m pip install pyserial mido
py -3 windows/fdd_gui.py
py -3 -m unittest discover -s windows -p test_fdd.py
```

EXEを作る場合はリポジトリのルートで実行します。

```powershell
py -3 -m pip install pyinstaller
py -3 -m PyInstaller --onefile --windowed --name FDDTool-Music windows/fdd_gui.py
```

## エクスプローラーで開く

[ImDisk](https://ltr-data.se/opencode.html#ImDisk) をインストールし、ディスク検出に対応した下記のファームウェアを基板に書き込みます。FDDのUSBシリアルが COM8 に見えている場合は、リポジトリのルートで次を実行します。環境に合わせてポート番号を指定してください。

```powershell
py -3 windows/fdd_mount.py --auto --port COM8
```

監視中は、1.44 MB FAT12のFDを挿入すると `A:\` を読み取り専用で開けます。抜くと割り当てが解除され、次のFDを挿入すると割り当て直します。書き込みやフォーマットをGUIで行うときは、監視を終了してシリアルポートを解放してください。コンソールから起動した監視は Ctrl+C で終了できます。

サインイン時に監視を起動するには、Windowsの `shell:startup` にショートカットを置きます。リンク先には Python とスクリプトの絶対パスを指定します。コンソールを表示せずに起動する場合は、Pythonのインストール先にある `pythonw.exe` を使います。

```text
"C:\path\to\pythonw.exe" "C:\path\to\fdd-arduino\windows\fdd_mount.py" --auto --port COM8
```

## ファームウェア

`firmware/transfer_fast.cpp` はArduino Uno相当のATmega328P（5 V・16 MHz）用です。Arduino AVRコアと [ArduinoFDC](https://github.com/dhansel/ArduinoFDC) を組み合わせてビルドします。ArduinoFDCはGPL-3.0で配布されている別プロジェクトです。ISPで書き込むときは、既存のフラッシュ、ブートローダー、ヒューズを事前に読み出してください。

DMF・XDF対応版をビルドするには、ArduinoFDCのコミット `c376c44166c2abf6bcc02500afa78697afab289f` に `firmware/arduinofdc-dmf.patch` を `git apply` し、変更後の `ArduinoFDC.cpp` と `ArduinoFDC.h` を転送用スケッチと同じフォルダーに置きます。

Arduino CLIでビルドする場合は、`FddTransfer` フォルダーに空の `FddTransfer.ino` を作り、`transfer_fast.cpp` とパッチ適用済みのArduinoFDCソースを入れます。IBM XDF版は下記の追加パッチとアセンブリファイルも必要です。親フォルダーから `arduino-cli compile --fqbn arduino:avr:uno FddTransfer` を実行します。

**イメージを復元** は標準1.44 MBとDMFの生イメージに対応します。DMFは1,720,320バイト、80シリンダ、両面、各面21セクターです。復元後に全3,360セクターを照合します。DMFのファイル単位の操作には対応していません。

実験機能として、X68000のXDFとPC-98標準2HDの生イメージ（1,261,568バイト、77シリンダ、両面、各面8セクター、1,024バイト/セクター）を復元できます。回転周期をINDEXから測り、360 rpmでは500 kbit/s、300 rpmでは約421 kbit/sを使います。300 rpm時はATmega328Pのタイマー分解能に合わせた近似値です。対象機での互換性は未確認です。

IBM／OS/2の3.5インチHD XDF生イメージ（1,884,160バイト）の実験的な復元にも対応します。約300 rpmのFDD、FTDIの低遅延接続、下記の実験用ファームウェアを使い、GUIの **イメージを復元** から実行します。シリンダ0の配置はfdutilsのxdfcopyに従い、イメージに対応する物理セクター（標準構成で670個）の内容とCRCを照合します。OS/2での読み取りは未検証です。[fdutilsのxdfcopy](https://sources.debian.org/src/fdutils/5.6-5/doc/xdfcopy.texi/)

IBM／OS/2 XDF向けの実験ビルドでは、上記パッチに続けて `firmware/arduinofdc-ibm-probe.patch` を適用し、`firmware/ibm_xdf_write.S` をスケッチと同じフォルダーに置きます。約300 rpmのドライブでシリンダ76の面1を単一の8 KiBセクターとして初期化したあと、`py -3 windows/probe_ibm_xdf.py COM8 <元のX68000テストイメージ>` で任意データの上書きとCRC照合を試せます。スクリプトは周辺セクターと既存の8 KiBセクターを読み取ってから書き込みます。

同じコマンドに `--mixed` を加えると、試験用トラックを512、1,024、2,048、8,192バイトの4セクターに初期化します。初期化直後と全4セクターの上書き後に、それぞれの内容とディスク上のCRCを照合します。

高速接続は500 kbpsから試し、データ照合に失敗した場合は低い速度を選びます。対応ファームウェアでは隣接2セクタをまとめて返し、通常フォーマットを10トラック単位で処理します。通常フォーマットはディスク全体を初期化します。クイックは標準FAT12の管理情報を初期化し、記録済みの不良クラスタを引き継ぎます。

### ディスク検出とA3のLED

A3（28ピンDIPの26番）から電流制限抵抗を介してLEDのアノードへ接続し、カソードをGNDに接続します。挿入中は点灯し、抜くと消灯します。検出にはD7の `/INDEX` とA2の `/DSKCHG` を使います。挿入時は回転パルスを検出するため、フォーマット情報は不要です。

転送プロトコルの `E`（引数0）は、正常応答に続いて挿入状態（0または1）と、挿入状態が変わるたびに増える8ビットのカウンターを返します。Windowsの監視はこの応答からディスク交換を検知します。

## 演奏

演奏対応の転送用ファームウェアを一度書き込むと、同じファームウェアで読み書きと演奏を切り替えられます。GUIの **演奏 → 試奏（音階）** または **演奏 → 音符JSONを開く** を使います。演奏中はディスク操作が無効になり、停止後に再開できます。ヘッドのステップで音を出すため、演奏にディスクは不要です。

**演奏 → MIDIを開く** で `.mid` や `.midi` を直接選べます。テンポを反映し、ドラムを除いて同時に鳴る音のうち最高音を採用します。曲全体をFDDの音域に合わせます。

音符JSONは `[[440, 200], [0, 100], [523, 300]]` のように `[周波数Hz, 長さms]` を並べます。周波数0は休符です。手元のMIDIは単音のJSONにも変換できます。

**演奏 → 音域の上限** で標準262 Hz、高音440 Hz、実験880 Hzを選べます。高音ではドライブによってヘッド位置の保護停止が起きることがあります。音符の長さは入力どおりです。

```powershell
py -3 tools/midi2fdd.py song.mid song.json
```

転送プロトコルの `M` は16ビットの周波数を受け取り、`O` で演奏を終了します。演奏の更新が約1秒途切れると自動停止します。演奏機能のない旧ファームウェアでも、GUIのディスク操作は利用できます。

## 実機結果

JU-256A046PCで、FDを抜くとA3のLEDが消え、挿入すると点灯することを確認しました。Windowsでは、挿入時に `A:` が現れ、抜き差し後に再割り当てされたドライブから14ファイルの一覧を読み取れました。サインイン時の自動起動はショートカットを設定し、動作確認は手動起動で行いました。

IBM／OS/2 XDF向けの実験では、JU-256A046PCとATmega328Pの既存構成で、片面1トラックに書いた8,192バイトの固定パターンを3回読み戻し、全バイトとディスク上のCRC（`1DC5`）が毎回一致しました。同じシリンダの反対面は元の8セクターと一致しました。

同じ8 KiBセクターにPCから疑似乱数と `55 AA` の繰り返しを順に送って上書きし、両方で8,192バイトすべてとディスク上のCRC（順に `5CFF` と `B806`）が一致しました。反対面の8セクターも元のイメージと一致しました。

シリンダ76の面1を512、1,024、2,048、8,192バイトの4セクターで初期化し、全セクターのデータとCRCを確認しました。全4セクターをサイズ別の疑似乱数データで上書きした後も、合計11,776バイトと各CRC（サイズ順に `5568`、`D955`、`B737`、`DD25`）が一致しました。反対面の8セクターも元のイメージと一致しました。

全ディスク試験では、テスト用FDを80シリンダで初期化し、書き込み中断から再開した後、XDFイメージに対応する全670物理セクターのデータとCRCが一致しました。書き込み側には受信中断時の再送を追加しました。

Panasonic JU-256A046PC、ATmega328P 16 MHz、FTDI低遅延接続で計測しました。72 KiBの読み取りは115,200 bpsで11.81秒、500 kbpsで7.01秒でした。1 Mbpsの通信照合はタイムアウトし、500 kbpsへ戻りました。通常フォーマットは76.6秒、256 KiBの書き込みと照合は55.8秒、全2,880セクタの読み取りは144.6秒でした。取り出した256 KiBは元データと一致しました。
